# Bazaar — Lexicon Migration: v6 rev.1 → v6 rev.2

**Date:** 17 April 2026
**Status:** Ready for implementation
**Target file:** `packages/shared/src/lexicons/`

This document lists every change required to bring the lexicon from v6 rev.1 to v6 rev.2. Each change includes the current text so the agent can confirm the file is in the expected state before editing, and the replacement text to apply.

All changes are non-breaking. No new required fields are introduced. No existing field names change. No records that already exist on any PDS are invalidated.

---

## Change 1 — `defs#bazaarIdentifier` top-level description

**File:** `diamonds.whereditgo.bazaar.defs` (likely `packages/shared/src/lexicons/defs.json` or equivalent)

**Context:** The `bazaarIdentifier` shared type carries a top-level `description` field on the object definition itself. In v6 rev.1 this description incorrectly states that identifiers are signed by the artist's ATProto keypair. The actual implementation signs with the app service keypair (`appDid`) because ATProto OAuth does not expose the artist's private key to the application. Ownership is proven transitively: the app signed the identifier using its service keypair and wrote the record to the artist's PDS via an OAuth session the artist granted.

**Locate this exact text:**

```
"description": "A self-issued, cryptographically signed identifier generated by the artist's backend at upload time. Serves as a non-colliding, ownership-evidentiary stand-in for institutional identifiers (ISRC, ISWC, UPC) until formal registration is obtained. Generated as base32(SHA-256(canonicalPayload)) where the payload always includes the artist's DID, ensuring global uniqueness without a registry. Signed by the artist's ATProto keypair — verifiable by resolving the artist's DID document. Mutability: id, sig, and generatedAt are immutable once written — mutating them destroys the evidentiary value of the assertion. The supersededBy* fields are the only mutable parts, populated when institutional registration is obtained.",
```

**Replace with:**

```
"description": "A self-issued, cryptographically signed identifier generated by the Bazaar backend at upload time. Serves as a non-colliding, ownership-evidentiary stand-in for institutional identifiers (ISRC, ISWC, UPC) until formal registration is obtained. Generated as base32(SHA-256(canonicalPayload)) where the payload always includes the artist's DID, ensuring global uniqueness without a registry. Signed by the Bazaar app service keypair (appDid) rather than the artist's personal ATProto keypair — ATProto OAuth does not expose the artist's private key to the application. Ownership is proven transitively: the app signed this identifier using its service keypair, and wrote the containing record to the artist's PDS using an OAuth session the artist granted. Verifiers resolve appDid to obtain the app's public verification key. Mutability: id, sig, kid, and generatedAt are immutable once written — mutating them destroys the evidentiary value of the assertion. The supersededBy* fields are the only mutable parts, populated when institutional registration is obtained.",
```

## Change 3 — `defs#bazaarIdentifier` add `kid` field

**File:** same as Change 1

**Context:** `kid` is a new optional string field identifying which app service keypair produced `sig`. It is needed for correct verification after a keypair rotation — the verifier uses `kid` to select the correct historical key from the app's DID document `verificationMethod` array rather than trying all keys. `kid` is a hint, not authoritative: verifiers still verify cryptographically and fall back to trying all non-revoked keys if the hinted key fails. Format convention: `app-key-{YYYY-MM-DD}` using the activation date of the keypair.

**Locate the `generatedAt` field block** (the last field before the `supersededBy*` fields):

```
"generatedAt": {
  "type": "string",
  "format": "datetime",
  "description": "Timestamp of identifier generation. Combined with the PDS record's creation timestamp forms a tamper-evident assertion of when ownership was first claimed."
},
```

**Replace with** (adds `kid` immediately after `generatedAt`):

```
"generatedAt": {
  "type": "string",
  "format": "datetime",
  "description": "Timestamp of identifier generation. Combined with the PDS record's creation timestamp forms a tamper-evident assertion of when ownership was first claimed. Immutable."
},
"kid": {
  "type": "string",
  "maxLength": 64,
  "description": "Key identifier for the app service keypair that produced sig. Format: app-key-{YYYY-MM-DD} where the date is the keypair's activation date, e.g. app-key-2026-04-17. Used by verifiers to select the correct historical key from the appDid DID document verificationMethod array when the app keypair has been rotated. kid is a hint — verifiers still verify cryptographically and should fall back to trying all non-revoked keys if the hinted key fails. Immutable."
},
```

## Change 6 — `purchase.receipt` add `kid` field

**File:** same as Change 5

**Context:** `kid` on `purchase.receipt` identifies which app service keypair produced `appSig`. This is required for receipt verification to remain possible after a keypair rotation, since old receipts on buyer PDSs cannot be updated. Without `kid`, verifiers must try all historical app keys to find the one that verifies. With `kid`, they can select the correct key directly from the app's DID document `verificationMethod` array.

**Locate the `appSig` field block** (after the replacement in Change 5 is applied) and add `kid` immediately after it. The `appSig` block after Change 5 ends with:

```
  "description": "Base64url signature by the Bazaar app service keypair (appDid) over SHA-256(purchasedAt:paymentRef:item.uri:listingCid:buyerDid). All five values are colon-delimited in the order listed. item.uri is the AT-URI from the item field. Verifiers reconstruct this payload from the receipt's plaintext fields and verify against the public key resolved from appDid — using kid to select the correct historical key if the keypair has been rotated. Immutable."
},
```

**Insert immediately after that closing `},`:**

```
"kid": {
  "type": "string",
  "maxLength": 64,
  "description": "Key identifier for the app service keypair that produced appSig. Format: app-key-{YYYY-MM-DD} where the date is the keypair's activation date, e.g. app-key-2026-04-17. Allows verifiers to select the correct historical key from the appDid DID document verificationMethod array without trying all keys exhaustively. kid is a hint — verifiers still verify cryptographically and should fall back to trying all non-revoked keys if the hinted key fails. Immutable."
},
```

`kid` is optional (not added to the `required` array). Receipts written before this migration do not carry `kid` and must be verified by trying all non-revoked app keys.

## Runtime changes required alongside lexicon changes

The lexicon changes above are descriptor-only — they do not change the shape of records already on any PDS. However, the signing code in `packages/server` must also be updated to populate `kid` on all newly written records.

**`packages/server` — all signing operations:**

Wherever the app service keypair signs a payload and produces `appSig` or `sig`, the `kid` of the active keypair must now be included in the written record. This applies to:

- `bazaarRid` generation → set `bazaarRid.kid`
- `bazaarWid` generation → set `bazaarWid.kid`
- `bazaarPid` generation → set `bazaarPid.kid`
- `purchase.receipt` write → set `receipt.kid`
- `purchase.consent` write → set `consent.kid`

The `kid` value is the identifier of the currently active app keypair, sourced from the `app_keys` table (`SELECT kid FROM app_keys WHERE status = 'active'`). See `26_4_17-key-rotation-strategy.md` for the `app_keys` table schema.

**`packages/server` — verification path:**

The download handler that verifies `purchase.receipt#appSig` must be updated to use `kid` as a key selection hint before falling back to trying all non-revoked keys. See `26_4_17-purchase-attestation.md` step 5 for the full verification flow.
