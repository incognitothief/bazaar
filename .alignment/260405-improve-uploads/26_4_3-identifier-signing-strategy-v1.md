# Bazaar — Self-Issued Identifier Signing Strategy
**Date:** 3 April 2026
**Status:** Settled decision, v1
**Applies to:** `bazaar:rid`, `bazaar:wid`, `bazaar:pid` — all `defs#bazaarIdentifier` instances

---

## Background

The Bazaar lexicon defines a `bazaarIdentifier` shared type used to generate self-issued, cryptographically signed identifiers that shadow institutional identifiers (ISRC, ISWC, UPC) until formal registration is obtained. Each identifier carries a `sig` field — a signature over a canonical payload that allows any third party to verify the identifier was generated by an authorised party.

The original lexicon description specified that `sig` is produced by the artist's ATProto keypair, making the identifier directly verifiable against the artist's DID document. This document records a deliberate departure from that specification and the reasoning behind it.

---

## The problem with artist keypair signing

ATProto OAuth gives Bazaar a session token that authorises reading and writing PDS records on the artist's behalf. It does not expose the artist's private key. The private key never leaves the artist's PDS or identity provider — this is by design and is a core security property of the ATProto identity model.

As a result, the Bazaar backend cannot produce a signature using the artist's keypair. Any design requiring the backend to sign with the artist's key is not implementable without either:

- Asking the artist to export and hand over their private key (unacceptable)
- Implementing client-side signing in the browser using whatever primitives the `@atproto/oauth-client-browser` SDK exposes (architecturally correct but not confirmed available)

Client-side signing via the ATProto SDK is the ideal long-term path. For the current build it is deferred pending confirmation of what signing primitives the SDK exposes.

---

## Settled decision: sign with the app service keypair

All `bazaarIdentifier` signatures are produced by the Bazaar app service keypair — the same keypair used to sign `purchase.receipt#appSig`.

The `sig` field on every `bazaarIdentifier` is:

```
base64url(appServiceKeypair.sign(SHA-256(canonicalPayload)))
```

Verifiers resolve `appDid` to obtain the app's public verification key and verify the signature against the reconstructed canonical payload. The app's DID document is the trust anchor.

---

## How ownership is proven transitively

Direct proof: the artist's keypair signed this identifier.
Transitive proof: the app signed this identifier, and the app wrote it to the artist's PDS using a session the artist granted via OAuth.

The transitive chain is:

```
1. Artist authenticated to Bazaar via ATProto OAuth
2. Artist granted Bazaar a scoped session to write records to their PDS
3. Bazaar generated the identifier and signed it with the app service keypair
4. Bazaar wrote the record containing the identifier to the artist's PDS using the OAuth session
5. The PDS accepted the write — the PDS is the authoritative store of the artist's records
```

A verifier who resolves the record from the artist's PDS, finds a valid `appSig` produced by the known `appDid`, and confirms the `artistDid` in the canonical payload matches the PDS owner, has established:

- The identifier was generated by a trusted app acting on behalf of this artist
- The artist authorised the app to act on their behalf at the time of generation
- The record is stored on the artist's own PDS, which the artist controls

This is weaker than a direct artist keypair signature but is sufficient for the intended purpose: establishing a timestamped, non-colliding, ownership-evidentiary claim prior to institutional registration. It is not a court-defensible ownership assertion — institutional registration (ISRC, ISWC, UPC) remains the standard for legal enforceability.

## Canonical payloads per identifier type

### `bazaar:rid` — Recording Identifier

Shadows ISRC. Lives on `catalog.item.digital` and `catalog.recording`.

```
payload = SHA-256(
  "bazaar:rid" + ":" +
  artistDid    + ":" +
  fileCid      + ":" +
  fileChecksum + ":" +
  createdAt
)

id = "bazaar:rid:" + base32(payload)
sig = base64url(appServiceKeypair.sign(payload))
```

`fileCid` and `fileChecksum` bind the identifier to a specific file. Two different files uploaded by the same artist produce different `bazaar:rid` values even if all other metadata is identical.

### `bazaar:wid` — Work Identifier

Shadows ISWC. Lives on `catalog.recording` and `catalog.composition`.

```
writers_canonical = sort(writers[].ipi ?? writers[].did ?? writers[].name).join(",")

payload = SHA-256(
  "bazaar:wid"       + ":" +
  artistDid          + ":" +
  compositionTitle   + ":" +
  writers_canonical  + ":" +
  createdAt
)

id = "bazaar:wid:" + base32(payload)
sig = base64url(appServiceKeypair.sign(payload))
```

Writers are canonicalised (sorted) before hashing to make the identifier order-independent. If no co-writer data is present, `writers_canonical` is the empty string.

### `bazaar:pid` — Product Identifier

Shadows UPC. Lives on `catalog.collection` only.

```
payload = SHA-256(
  "bazaar:pid"  + ":" +
  artistDid     + ":" +
  collectionUri + ":" +
  releaseDate
)

id = "bazaar:pid:" + base32(payload)
sig = base64url(appServiceKeypair.sign(payload))
```

`collectionUri` is the AT-URI of the `catalog.collection` record. This is not available until after the collection record is written. `bazaarPid` is therefore generated and written in a second `putRecord` pass after the collection record exists, updating the collection record with the `bazaarPid` field populated.

## Verification flow

Any third party can verify a `bazaarIdentifier` without contacting the Bazaar backend:

1. Obtain the `bazaarIdentifier` object from the PDS record (`bazaarRid`, `bazaarWid`, or `bazaarPid` field)
2. Obtain `appDid` — present on `purchase.receipt` records, or known from the Bazaar app's published DID
3. Resolve `appDid` via the AT Protocol DID resolution mechanism to obtain the app's public verification key
4. Reconstruct the canonical payload from the record fields (per the payload definitions above)
5. Verify `sig` using the public key against the reconstructed payload
6. Confirm `artistDid` in the payload matches the DID that owns the PDS where the record lives

If all checks pass, the identifier was generated by the Bazaar app acting on behalf of the artist who owns this PDS.

## Lexicon amendment required

The `defs#bazaarIdentifier` description in the lexicon currently reads:

> "Signed by the artist's ATProto keypair — verifiable by resolving the artist's DID document."

This must be updated in the next lexicon version (v6) to:

> "Signed by the Bazaar app service keypair (`appDid`) rather than the artist's personal ATProto keypair. The app's keypair is used because ATProto OAuth does not expose the artist's private key to the application. Ownership is proven transitively: the app signed this identifier using its service keypair, and wrote the containing record to the artist's PDS using an OAuth session the artist granted. Verifiers resolve `appDid` to obtain the public key for signature verification. The `artistDid` embedded in the canonical payload identifies the artist on whose behalf the identifier was generated."

The `sig` field description must also be updated from:

> "Base64url signature by the artist's ATProto keypair over the canonical identifier payload. Verifiable by resolving the artist's DID document to obtain the public key."

To:

> "Base64url signature by the Bazaar app service keypair over the canonical identifier payload. Verifiable by resolving `appDid` to obtain the app's public verification key. The artist's DID is embedded in the payload, not used as the signing key."

## Future upgrade path

If `@atproto/oauth-client-browser` exposes a signing primitive that allows the browser session to sign arbitrary payloads using the artist's key material, the signing strategy can be upgraded:

- Identifier generation moves client-side
- `sig` is produced by the artist's key in the browser
- `sig` becomes verifiable directly against the artist's DID document without reference to `appDid`
- The `appDid` trust anchor is no longer required for identifier verification (though it remains on `purchase.receipt`)

This upgrade is non-breaking: existing identifiers signed with the app keypair remain valid under the transitive trust model. New identifiers signed with the artist keypair are verifiable more directly. Both can coexist — verifiers check `sig` against `appDid` first, then against the artist's DID document if the first check fails.

No lexicon change is required for this upgrade beyond updating the field descriptions again.

---

## What this does not cover

- `purchase.receipt#appSig` — always signed by the app service keypair by design, no change
- `purchase.consent#appSig` — same
- Institutional identifiers (ISRC, ISWC, UPC) — assigned by external registries, not signed by Bazaar
- Key rotation or revocation for the app service keypair — out of scope for the current build
